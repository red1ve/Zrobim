# Зробим

Веб-версия для телефона. Клиент находит услугу, мастер принимает заявку, клиент выбирает способ демонстрационной оплаты и получает подтверждённую запись.

## Запуск

Понадобятся .NET SDK 10 и PostgreSQL. Для проверок также нужны Node.js 20+ и инструменты PostgreSQL.

1. Создайте отдельную базу и пользователя PostgreSQL с правами на её схему и установку `btree_gist`.
2. Заполните `.env` по образцу из `.env.example`. Для `Jwt__SigningKey` используйте отдельный случайный секрет длиной не менее 32 байт.
3. Из корня проекта выполните:

   ```powershell
   dotnet tool restore
   dotnet build Zrobim.slnx
   dotnet ef database update --no-build --project src/Zrobim.Api
   dotnet run --no-build --project src/Zrobim.Api --launch-profile http
   ```

Локальный адрес — [localhost:5262](http://localhost:5262/). Маршрут `/health` проверяет соединение с базой.

## Аккаунты для проверки

Клиент и мастер регистрируются через интерфейс. Для первой категории понадобится администратор. Зарегистрируйте отдельный тестовый аккаунт как клиента и назначьте ему роль через SQL под владельцем тестовой базы. Подставьте email только что созданного аккаунта и проверьте, что команда изменила одну строку. Затем войдите повторно.

```sql
UPDATE users
SET role = 'ADMIN', updated_at = now()
WHERE lower(email) = lower('ваш-отдельный-тестовый-аккаунт') AND role = 'CLIENT';
```

Администратор создаёт категорию и одобряет мастера в кабинете. Дополнительный демокаталог можно загрузить из `db/demo/catalog.sql` после миграций.

## Повторяемые проверки

- `./db/tests/run-tests.ps1` проверяет ограничения PostgreSQL в отдельной схеме с откатом транзакции. Ключ `-Reference` проверяет эталонный SQL, `-NoBuild` использует уже собранный проект.
- `node tests/smoke.mjs` прогоняет запущенное приложение через API. Скрипт создаёт данные с уникальным префиксом `smoke-`, поэтому запускайте его на выделенной тестовой базе. Укажите адрес и данные тестового администратора через переменные `ZROBIM_SMOKE_BASE_URL`, `ZROBIM_SMOKE_ADMIN_EMAIL` и `ZROBIM_SMOKE_ADMIN_PASSWORD`. Для сценария оплаты нужен включённый деморежим.

## Общий тестовый стенд

### Render

В корне проекта есть `Dockerfile` и `render.yaml` для публичного демостенда. Загрузите исходники в репозиторий GitHub и выберите его при создании Blueprint в Render. Включены отдельная PostgreSQL, миграции при запуске, демокаталог и имитация оплаты. Ссылка на сервис появится в панели Render после успешного запуска.

Перед отправкой в GitHub проверьте список файлов через `git status --short`. Для демостенда нужны `src`, `db`, `tests`, `Dockerfile`, `.dockerignore`, `render.yaml`, `.env.example`, `README.md`, `Zrobim.slnx` и `dotnet-tools.json`. Локальные секреты остаются в `.env`.

Посетители могут нажать «Посмотреть каталог» на стартовом экране. Для показа всего сценария зарегистрируйте отдельного клиента. Логин мастера `catalog-master@zrobim.example`, пароль находится в переменной `DemoCatalog__MasterPassword` в панели сервиса Render. Этот пароль назначается при первом заполнении базы.

На бесплатном тарифе первый запрос после простоя может быть медленным. Тестовая PostgreSQL действует 30 дней.

### Свой сервер

Соберите пакет командой `dotnet publish src/Zrobim.Api/Zrobim.Api.csproj -c Release -o publish/zrobim-staging`. На хосте понадобится ASP.NET Core Runtime 10. Примените миграции к выделенной базе стенда из исходного проекта, затем запускайте опубликованный `Zrobim.Api.dll` из каталога публикации.

Задайте секреты через настройки процесса. Для прямого запуска Kestrel с сертификатом формата PFX нужны следующие переменные:

```text
ASPNETCORE_ENVIRONMENT=Staging
ASPNETCORE_URLS=https://0.0.0.0:443
Kestrel__Certificates__Default__Path=<путь к PFX>
Kestrel__Certificates__Default__Password=<пароль сертификата>
AllowedHosts=<домен стенда>
ConnectionStrings__Default=<подключение к базе стенда>
Jwt__SigningKey=<секрет стенда>
DemoPayment__Enabled=true
```

Если HTTPS завершает прокси на том же хосте, задайте `ASPNETCORE_URLS=http://127.0.0.1:5262` и уберите настройки PFX из процесса приложения. Прокси должен передавать исходный `Host`, а также выставлять `X-Forwarded-Proto` и `X-Forwarded-For` для каждого запроса.

Выдайте команде HTTPS-адрес и заведите отдельные тестовые аккаунты. Направьте stdout и stderr в журнал сервиса и проверьте `/health` после запуска. Планируйте копирование отдельной базы командой `pg_dump --format=custom --file=zrobim-staging.dump --dbname=zrobim_staging` с параметрами подключения стенда. Проверяйте копию восстановлением через `pg_restore --exit-on-error --dbname=zrobim_restore zrobim-staging.dump` в отдельную пустую базу.

Деморежим включается явно на стенде. Платежи с провайдерами `demo_card` и `demo_erip` обозначают симуляцию и хранятся вместе с остальными тестовыми данными.

## Приёмка на телефонах

1. В двух браузерах войдите под разными аккаунтами клиента и мастера. У мастера должна быть одобренная анкета, активная услуга и часы на ближайшие дни.
2. Клиент находит услугу, выбирает время, отправляет заявку и видит её в «Записях». Мастер открывает уведомление и принимает заявку.
3. Клиент обновляет «Записи», нажимает «Оплатить», выбирает карту или ЕРИП и проверяет экран успеха. После обновления страницы в «Записях» обе стороны видят «Подтверждена».
4. На другой заявке проверьте «Отклонить» или «Отозвать». Клиент должен снова увидеть освободившееся время в каталоге.
5. На экранах записи и оплаты проверьте, что клавиатура, узкий экран и потеря связи не скрывают важные кнопки, а ошибку можно прочитать и повторить действие.
